# План проектирования базы данных

## 1. Назначение
База данных предназначена для:
* просмотра партнеров;
* редактирования данных партнеров;
* хранения справочника товаров;
* хранения истории продаж товаров партнерам.

Схема спроектирована в **третьей нормальной форме (3NF)**.

---

## 2. Сущности
В схеме используются три основные сущности:

| Таблица    | Назначение                       |
| ---------- | -------------------------------- |
| `partners` | Данные партнеров                 |
| `products` | Справочник товаров               |
| `sales`    | История продаж товаров партнерам |

Таблица `sales` связывает партнеров и товары и хранит сведения о каждой продаже: дату, количество и общую сумму.

---

## 3. Таблица `partners`
Хранит данные партнеров.

| Поле            | Тип             | Ограничения                   | Назначение                        |
| --------------- | --------------- | ----------------------------- | --------------------------------- |
| `partner_id`    | `INTEGER`       | `PRIMARY KEY`                 | Уникальный идентификатор партнера |
| `company_name`  | `VARCHAR(255)`  | `NOT NULL`                    | Наименование компании             |
| `inn`           | `VARCHAR(12)`   | `NOT NULL`, `UNIQUE`, `CHECK` | ИНН партнера                      |
| `contact_email` | `VARCHAR(255)`  | `NOT NULL`, `UNIQUE`          | Контактный email                  |
| `phone`         | `VARCHAR(32)`   | —                             | Телефон партнера                  |
| `rating`        | `DECIMAL(2, 1)` | `CHECK`                       | Рейтинг партнера                  |

Для поля `inn` используется проверка длины:

```sql
CHECK (char_length(inn) IN (10, 12))
```

Для рейтинга используется проверка допустимого диапазона:

```sql
CHECK (rating BETWEEN 0 AND 5)
```

Поля `phone` и `rating` могут содержать `NULL`, поскольку во входных данных эти значения могут отсутствовать.

---

## 4. Таблица `products`
Хранит справочник товаров.

| Поле           | Тип              | Ограничения          | Назначение                      |
| -------------- | ---------------- | -------------------- | ------------------------------- |
| `product_id`   | `INTEGER`        | `PRIMARY KEY`        | Уникальный идентификатор товара |
| `article`      | `VARCHAR(64)`    | `UNIQUE`             | Уникальный артикул товара       |
| `product_name` | `VARCHAR(255)`   | `NOT NULL`, `UNIQUE` | Наименование товара             |
| `unit`         | `VARCHAR(32)`    | —                    | Единица измерения               |
| `price`        | `DECIMAL(12, 2)` | `CHECK >= 0`         | Текущая базовая цена товара     |

Поля `article`, `unit` и `price` не имеют ограничения `NOT NULL`, поскольку предоставленный файл продаж содержит только название товара и не содержит артикул, единицу измерения или текущую базовую цену.

Для цены используется ограничение:

```sql
CHECK (price >= 0)
```

Поле `product_name` имеет ограничение `UNIQUE`, поскольку при импорте название товара используется для определения соответствующей записи в таблице `products`.

---

## 5. Таблица `sales`
Хранит историю продаж товаров партнерам.
Исходные данные о продажах имеют следующую структуру:

```text
sale_id
partner_id
product_name
sale_date
quantity
total_amount
```

В нормализованной структуре поле `product_name` заменяется на внешний ключ `product_id`.

| Поле           | Тип              | Ограничения               | Назначение                       |
| -------------- | ---------------- | ------------------------- | -------------------------------- |
| `sale_id`      | `INTEGER`        | `PRIMARY KEY`             | Уникальный идентификатор продажи |
| `partner_id`   | `INTEGER`        | `NOT NULL`, `FOREIGN KEY` | Партнер, которому продан товар   |
| `product_id`   | `INTEGER`        | `NOT NULL`, `FOREIGN KEY` | Проданный товар                  |
| `sale_date`    | `DATE`           | `NOT NULL`                | Дата продажи                     |
| `quantity`     | `INTEGER`        | `NOT NULL`, `CHECK > 0`   | Количество проданного товара     |
| `total_amount` | `DECIMAL(12, 2)` | `NOT NULL`, `CHECK >= 0`  | Общая сумма продажи              |

Связь с партнером:

```sql
FOREIGN KEY (partner_id)
REFERENCES partners(partner_id)
ON DELETE RESTRICT
```

`ON DELETE RESTRICT` запрещает удалить партнера, если для него уже существуют записи в истории продаж.

Связь с товаром:
```sql
FOREIGN KEY (product_id)
REFERENCES products(product_id)
ON DELETE RESTRICT
```

Товар нельзя удалить, если он уже использовался в истории продаж.

Для количества используется ограничение:
```sql
CHECK (quantity > 0)
```

Для общей суммы продажи:
```sql
CHECK (total_amount >= 0)
```

---

## 6. Связи между таблицами

Между таблицами используются следующие связи:

* `partners 1:N sales` — у одного партнера может быть много продаж;
* `products 1:N sales` — один товар может встречаться во многих продажах.

Таким образом, таблица `sales` связывает партнера с конкретным товаром и хранит информацию о совершенной продаже.

Схема:

```text
partners
   |
   | 1:N
   |
 sales
   |
   | N:1
   |
products
```

---

## 7. Схема соответствует **третьей нормальной форме (3NF)**, потому что:
* данные партнера хранятся только в таблице `partners`;
* данные товара хранятся только в таблице `products`;
* таблица `sales` содержит ссылки на партнера и товар вместо дублирования их данных;
* название товара не повторяется в каждой записи о продаже;
* название компании, ИНН, email и телефон партнера не повторяются в таблице `sales`;
* каждый неключевой атрибут зависит непосредственно от первичного ключа своей таблицы.

Например, название товара зависит от `product_id` и хранится только в `products`.

В таблице `sales` вместо названия товара хранится:
```text
product_id
```

А вместо данных партнера:
```text
partner_id
```

Сведения, относящиеся непосредственно к продаже:
```text
sale_date
quantity
total_amount
```

хранятся в таблице `sales`, поскольку они зависят от конкретной продажи `sale_id`.

---

## 8. Соглашение об именовании
Для всей схемы используется единый стиль:

* названия таблиц — во множественном числе;
* названия таблиц и полей — в `snake_case`;
* первичные ключи имеют формат `<entity>_id`;
* внешние ключи используют имя соответствующего первичного ключа.

Примеры:

```text
partners
partner_id

products
product_id

sales
sale_id
partner_id
product_id

total_amount
sale_date
```

## 11. Итоговая структура

Итоговая структура базы данных:

```text
partners
--------
partner_id PK
company_name
inn
contact_email
phone
rating


products
--------
product_id PK
article
product_name
unit
price


sales
--------
sale_id PK
partner_id FK -> partners.partner_id
product_id FK -> products.product_id
sale_date
quantity
total_amount
```

Такая структура соответствует исходным данным, позволяет хранить историю продаж и исключает избыточное дублирование информации о партнерах и товарах.
